# Krite Protocol v1

The machine contract is JSON Schema (2020-12): [request](request.schema.json), [response](response.schema.json), [error](error.schema.json). This document covers the semantics and constraints that the schemas cannot express. Terms (State, Probability, Confidence, etc.) follow the [ARCHITECTURE.md Glossary](../../ARCHITECTURE.md#2-glossary).

## 1. Endpoint

```http
POST /v1/systemone
Content-Type: application/json
```

Other endpoints (health, model list, etc.) are defined with the runtime server and are out of scope here.

## 2. Request

Examples: [choice.request.json](examples/choice.request.json), [multi.request.json](examples/multi.request.json)

| Field | Required | Description |
|---|---|---|
| `model` | no | Model id (e.g. `krite-0.15b-v1`). If omitted, the server default model is used. |
| `state` | yes | String or JSON object. An object is canonicalized with RFC 8785 (JCS); the canonical string is the encoder input and the cache key input. Objects that differ only in key order or whitespace are the same state. |
| `questions` | yes | `{<question id>: Question}`, at least 1 entry (server limit, §4). Id pattern `^[A-Za-z0-9_.-]{1,64}$`. Ids map answers to questions and are not model inputs. |

The Question shape depends on `type`. Write the judging criteria in `instructions`. Criterion names and descriptions are also model inputs. Any language the model supports may be used in `state`, `instructions`, and criteria.

| `type` | `criteria` | Notes |
|---|---|---|
| `choice` | object `{<option name>: description \| null}`, at least 1 entry (server limit, §4) | Object key order has no meaning (I1). |
| `score` | array `[level_0, level_1, …]`, at least 1 item (server limit, §4), no duplicates | Array order is level order. |
| `noul` | optional object `{"true"?: description \| null, "false"?: description \| null}` | May be omitted. |

## 3. Response

Examples: [choice.response.json](examples/choice.response.json), [multi.response.json](examples/multi.response.json)

| Field | Description |
|---|---|
| `model` | Exact id of the model that answered (including any quantization suffix). |
| `answers` | `{<question id>: Answer}`. Contains every question id from the request. |
| `usage.input_tokens` | Total input tokens tokenized for this request. |
| `usage.output_tokens` | Always `0` (no generation). |
| `latency_ms` | Server-side runtime latency, from after HTTP parsing to before serialization. |

Answer shapes:

| `type` | Fields |
|---|---|
| `choice` | `choice` (argmax name), `probabilities` `{<option name>: p}`, `confidence` |
| `score` | `score` = Σ i·p_i (may fall between levels), `legend` `{"0": level_0, …}`, `probabilities` `{<level name>: p}`, `confidence` |
| `noul` | `noul` = P(true). No `confidence`. |

- `probabilities` sum to 1 ± 1e-6.
- `confidence` = `1 − H(p) / ln K` (1.0 when K = 1). It is not a probability.
- Choice argmax ties are broken by ascending Unicode codepoint order of option names.
- Score `probabilities` are serialized in level order (level_0 first).

## 4. Limits

| Item | Default limit | `error.type` on violation |
|---|---|---|
| questions | 64 | `too_many_questions` |
| criteria per question | 255 | `too_many_options` |
| state length | 8192 tokens (model tokenizer) | `state_too_long` |
| request body | 4 MiB | `invalid_request` |

Limits are server defaults, not protocol limits. They are configurable, and changing them is not a protocol change. The JSON Schemas therefore set no upper bounds; the server enforces its configured limits. The server reports limit violations with the specific `error.type` above rather than a generic schema error.

## 5. Errors

Body format: [error.schema.json](error.schema.json). Example: [too-many-options.error.json](examples/too-many-options.error.json)

| HTTP | `error.type` |
|---|---|
| 422 | `invalid_request`, `state_too_long`, `too_many_questions`, `too_many_options`, `unknown_model` |
| 500 | `internal_error` |

`error.param` is the dotted path of the problem location (`questions.route.criteria`), or `null` when there is none. This format is Krite's own definition. Jev SDK behavior is checked by the compatibility suite.

## 6. Headers

| Response header | Value |
|---|---|
| `x-krite-request-id` | Request id |
| `x-typesafe-request-id` | Same value as `x-krite-request-id` (compatibility) |
| `x-krite-state-cache` | `hit` \| `miss` |
| `x-krite-timing` | Per-stage ms, e.g. `tokenize=0.4;encode=12.1;decide=1.3;calibrate=0.05` |

Krite extension data goes only in headers, never in the response body. Extra body fields could break Jev SDK parsing.

## 7. Differences from Jev

| Item | Krite v1 | Jev / Kev |
|---|---|---|
| state limit | 8192 tokens | 65,536 tokens (per Kev) |
| question limit | 64 | unconfirmed |
| error body | Krite definition (§5) | unconfirmed |
| `confidence` | normalized-entropy based (§3) | definition not public; numeric meaning may differ |
| `usage.output_tokens` | always 0 | - |
| decisions | wire compatibility only | no behavioral equivalence |

## 8. Open items (confirm with the official Jev SDK)

- Actual key spelling of noul `criteria`. Kev docs show `"true?"`/`"false?"`, interpreted here as optional keys `true`/`false`. Confirm with official SDK serialization.
- Jev error body format and status codes.
- Jev question limit.
- Score `probabilities` keys and `usage.output_tokens`. Two engines that claim Jev wire compatibility (Kev, cbjev) key score `probabilities` by level index (`"0"`, `"1"`, …) rather than level name and may return nonzero `output_tokens`; cbjev also omits `latency_ms` and adds top-level fields. If the official SDK confirms the index form, v1 adopts it (see [baselines.md](../baselines.md)).
